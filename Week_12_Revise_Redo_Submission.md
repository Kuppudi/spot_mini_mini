# Week 12: Revise, Redo

For the revise-redo part of our project, we mainly focused on improving the reliability of the robot walking pipeline and cleaning up ideas that looked promising at first but were not actually helping us move toward a better final system. Since our project is based on training and testing SpotMini walking models in simulation, a lot of our revisions happened in the areas of locomotion stability, playback reliability, environment consistency, and day-to-day usability while we were experimenting.

One of the first revisions we made was to how training runs and saved model runs were discovered by the code. Earlier in the project, some of the tools expected a folder called `training_runs`, while other parts of the repository were using `training runs`. That sounds small, but it created real problems when we tried to warm-start a model, auto-discover a teacher policy, or replay a saved run. The code would fail for path reasons even when the actual model files were there. We revised the run-discovery logic so the platform could recognize both folder naming styles. We chose this path because it removed a very avoidable source of failure and made the whole training and playback process more stable.

Another big revision was improving how playback handles model and environment mismatches. While testing, we found that if we changed the observation setup, such as forcing IMU yaw features on a model that had been trained without them, the result could be a low-level checkpoint mismatch. Instead of giving a clear explanation, the old behavior could look like a confusing crash. We revised playback so those cases now fail more safely and provide a more readable explanation. This mattered because during our project we trained several related models with different features, so it was easy to accidentally try the wrong playback configuration. We wanted that mistake to be recoverable instead of looking like the entire platform was broken.

As we trained different walking models, we also revised our actual strategy and not just the code. At one point we were testing yaw-related IMU ideas somewhat independently, but over time we realized that yaw by itself was not really the goal. What we actually cared about was whether the robot could walk straighter, stay more stable, and eventually transfer better to rough-terrain walking. That led to an ideology change in the project. Instead of asking whether a feature was interesting on its own, we started asking whether it helped forward walking, turning behavior, terrain handling, or model transfer. That shift helped us stop spending too much time on isolated features that did not improve the larger locomotion problem.

We also revised the robot’s posture and gait geometry while testing both manual control and learned walking. During experimentation, we saw issues like the rear of the robot sitting too high, the body looking too toy-like, forward walking drifting, strafe directions being inconsistent, and some turning behaviors acting opposite of what we intended. To improve this, we adjusted body height offsets, body pitch bias, gait geometry profiles, stride balance, swing behavior, and directional handling in the motion pipeline. We chose this path because visually believable and mechanically stable movement was important not only for presentation, but also for model quality. If the base gait logic is wrong, the learning system ends up training on bad motion behavior.

Another revision we made was to the manual control and testing workflow. Earlier testing relied more on mixed controls and interfaces that made it harder to tell whether a problem came from the learned model, the gait logic, or the user interface. We changed this into a more direct app-style manual control system with clearer modes like `Manual Mode` and `Test PPO Model`. This helped us test the PyBullet simulation more cleanly and made it easier to separate manual tuning problems from learned-policy problems. We chose that path because the project moved faster when we could isolate one layer of the system at a time.

We also improved how we compare models. In the beginning, it was easy to say one run “looked better” than another, but that was too subjective. So we added comparison support that reports reward, speed, distance, height error, falls, and timeout behavior. This was a strategy revision as much as a code revision. We moved from mostly visual judging to a combination of visual and quantitative evaluation. We chose this because when training multiple models, especially slight variants of the same walking approach, we needed clearer evidence for whether a change was actually helping.

There were also a few concepts we reviewed and kept coming back to during this phase. One was the tradeoff between stability and aggressiveness. A robot can be made safer by reducing stride aggressiveness, but if we overdo that, it starts to move unrealistically or too slowly. Another concept was observation consistency in reinforcement learning. If the environment state changes, even in ways that seem small, the saved model may no longer match the environment it was trained in. We also had to think carefully about when to solve a problem in the simulator and when to solve it in the learning setup. Some problems were clearly gait-logic issues, like wrong strafe direction or body posture imbalance. Others were better handled through training configuration and environment design.

For now, we chose to stay focused on building a more stable and explainable pipeline instead of constantly adding new experimental features. That means we prioritized consistent run discovery, safer playback, better gait realism, clearer manual testing, and more useful model comparison. We chose this path because a stable system that trains, replays, compares, and demonstrates correctly is more valuable for our project than a system with a larger number of half-working features.

Overall, the revise-redo phase helped us improve both our code and our thinking. We did not just patch bugs. We also became more selective about what kinds of features were worth pursuing, and we moved toward a project structure that is easier to debug, easier to demonstrate, and more consistent as we continue training different walking models.
